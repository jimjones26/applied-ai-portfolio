Current project

Keel — every action authorized, every action recorded

Keel: a platform kernel for company software

Keel is a platform kernel that company software would run on. It is one service where every action — by a person, a backend service, or an AI agent — has to be explicitly authorized for that company and then recorded as evidence. The kernel covers identity, permissions, company data, connections to outside systems, and calls to AI models, all through the same audited path, with the rules checked against a formal contract written in Zig and stored in PostgreSQL. Apps and company-specific products sit on top as data and clients.

It is the fourth iteration of my architecture thinking, and it is the architecture I now consult on. No customers or shipped product yet. The Substrate case studies below test the same authorization-and-evidence ideas against the OWASP LLM Top 10.

Selected case studies (4 of 20)

Substrate — The Backdoor It Can’t Land

Shows a poisoned model’s data leak blocked and its redirected payout held for a human.

A relief-disbursements desk pulls its caseworker model from an open marketplace — and the artifact is poisoned — a fine-tuned sleeper backdoor that fires on a benign-looking trigger to redirect a payout and leak confidential financials. The publisher signed the artifact and the signature checks out, so the model binds, runs, and betrays. OWASP LLM04 is Data and Model Poisoning. What it shows: the substrate doesn’t detect the backdoor — it bounds it. The exfil hits a default-deny marking-clearance egress gate (EgressNotPermitted) with no human in the loop, and the redirected disbursement is suspended by a review policy as a durable PendingDecision that executes nothing without a human. Neither wall is bespoke to this attack — both are frozen substrate, downstream of provenance entirely. A live slice on Substrate against OWASP LLM04 (Data & Model Poisoning).

Substrate — The Model It Can’t Bind

Shows an unattested model being refused before it ever runs.

A model-routing company serves every customer task on a third-party specialist — its supply chain is its product — and a PoisonGPT-style tampered model is published into a source it curates. OWASP LLM03 is Supply Chain: a third-party model enters the runtime with no provenance and an agent binds it. What it shows: binding an unattested model is made unconstructable, not merely discouraged — a production provider requires an Ed25519 attestation, so the poisoned model is refused at the binding boundary before a single token (ModelProvenanceUnverified), the refusal is sealed as a first-class DENIED envelope, and the same model is confined — not banned — to an eval lane where default-deny egress keeps customer data away from it. Honest about the one link it can’t close: fingerprinting opaque vendor weights. A live slice on Substrate against OWASP LLM03 (Supply Chain).

Substrate — The Output It Can’t Weaponize

Shows attacker-written alert text that cannot run as a shell command or a browser script.

An incident console feeds attacker-controlled alert text at two sinks that would act on it — a command sink that runs diagnostics over a workspace, and a public HTML status page. OWASP LLM05 is Improper Output Handling: untrusted output reaching a shell, an eval, or a browser that renders it. What it shows: the dangerous crossing is made unconstructable, not merely discouraged — inbound alerts are marked untrusted and every sink is default-deny, the cleared command runs argv-exact with no shell, an irreversible remediation suspends for human review, and HTML-encoding lives on the recipient — so the deliberately-naive {@html} status page renders a laundered <script> / <img onerror> as inert text. A live slice on Substrate against OWASP LLM05 (Improper Output Handling).

Substrate — The Prompt It Can Publish

Shows a bank publishing its full system prompt and staying secure, because no control lives in the prompt.

A retail bank publishes its AI assistant's complete system prompt in the console — under a banner saying it is not a secret — and the bank is still secure. OWASP is blunt: the prompt is not a secret and must not be a security control; the real failure is the credential, limit, or permission a developer wrongly embeds in it. What it shows: knowing every word of the prompt buys an attacker nothing, because every control lives where a leaked prompt cannot reach it — the model credential below the spine, the $5,000 daily limit in a Policy, the money in the balance — and a credential pasted into a prompt cannot even deploy. A live slice on Substrate against OWASP LLM07 (System Prompt Leakage).
